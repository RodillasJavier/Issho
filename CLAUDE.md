# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Issho (一緒) is a community-driven anime tracking platform: users add reviews, ratings, and status updates for anime, vote and comment on entries, and manage a personal watchlist. Frontend-only SPA (Vite + React 19 + TypeScript) backed by Supabase (Postgres, Auth, Storage), with anime metadata sourced from the AniList GraphQL API. Seasons of one show are grouped into franchises via AniList's relations graph (`franchise_key` on `anime`).

## Commands

Standard Vite/npm scripts — see `package.json`. Tests: `npm test` (unit, needs nothing), `npm run test:rls` (needs `npm run db:up`), `npm run test:e2e` (needs `supabase start`). `npm run db:reset` replays migrations — required after changing one, since the E2E seed step does not. Details in `docs/TESTING.md` / `docs/CICD.md`.

Environment variables (`.env`, not committed): `VITE_SUPABASE_ANON_KEY`; optionally `SUPABASE_SERVICE_ROLE_KEY` for direct-write runs of `scripts/backfill-anilist.ts` (one-time MAL→AniList backfill, already executed — resumable/idempotent; `--dry-run` and `--emit-sql` work with the anon key). `VITE_SUPABASE_URL` is optional — `src/supabase-client.ts` falls back to the production URL, so set it only to point at the local stack (Playwright does). See `.env.example`.

## Architecture

**Data flow layers** — keep new code in the matching layer rather than mixing concerns:
- `src/services/anilistApi.ts` — thin client for the external AniList GraphQL API only (single POST endpoint, rate-limited ~50 req/min client-side, `isAdult: false` search filter, typed 429/403 errors). Knows nothing about Supabase.
- `src/services/anilistFranchise.ts` — resolves a `franchise_key` from AniList's relations graph: walk `PREQUEL` edges to the chain head (the key), plus a one-hop `PARENT` attach for side content. Never follows `SIDE_STORY` (parent→child direction), `SPIN_OFF`, `CHARACTER`, `SUMMARY`, or `ALTERNATIVE`; never compares titles. DB lookups are injected via `ResolveContext`, keeping this layer Supabase-free (the backfill script reuses it).
- `src/api/animeSearch.ts`, `src/api/animeImport.ts`, `src/api/animeMapping.ts` — bridge AniList and the local DB: combined local+AniList search, field/status mapping (`animeMapping.ts` is kept free of the Supabase client so `scripts/` can import it under Node), and import via upsert on `anilist_id` (with a 7-day staleness refresh). Importing any season also imports its whole backbone (every sequel-chain member), best-effort, so franchises arrive complete. Legacy columns `external_id`/`mal_id` hold the old MAL id; `anilist_id` is the external key going forward.
- `src/services/supabase/*.ts` — one file per domain (`profiles.ts`, `friendships.ts`, `userAnimeList.ts`, `userFranchiseList.ts`, `userLists.ts`, `entries.ts`, `votes.ts`) wrapping direct Supabase queries. Functions throw `Error(error.message)` on failure rather than returning error objects — callers should expect exceptions, not `{ error }` tuples. `entries.ts`'s `fetchEntriesWithCounts` is the bulk activity-feed fetch (wraps the `get_entries_with_counts` Postgres RPC — a `LATERAL`-joined function returning `likes_count`/`dislikes_count`/`comment_count`/`user_vote` per entry — then joins anime/profile data in memory) shared under one `entriesQueryKey(userId)` TanStack Query key by the homepage feed and the Friends page's per-friend previews, so the second consumer to mount never triggers a refetch. The key is viewer-scoped because the rows are RLS-scoped — sharing a bare `["entries"]` key across sessions would leak the previous user's feed from cache. `entries.ts` also exports `fetchPublicFeed`/`fetchPublicEntry` for logged-out visitors (see **Visibility** below). It also exports `applyVoteToEntriesCache`/`incrementEntryCommentCount`, the only place that knows how to patch that cache after a vote or comment — called from every mutation site (`LikeButton`, `EntryVoteButtons`, `CommentSection`) instead of each reimplementing it. `friendships.ts` exports `getOtherProfile(friendship, viewerId)` to resolve a friendship row to whichever party isn't the viewer.
- `src/types/database.types.ts` — hand-maintained TypeScript types mirroring the Supabase schema (not auto-generated). Update this file manually when the schema changes.

**Auth**: `AuthContext`/`AuthProvider` (`src/context/`) wrap Supabase Auth session state (`onAuthStateChange`) and expose `signInWithEmail`/`signUpWithEmail`/`signOut`/`user`/`initializing`. `initializing` is true only until the first session lookup settles: **any consumer that renders one thing signed-in and another signed-out must wait on it**, or it paints the signed-out branch for a logged-in user. Components that render `null` when `!user` are already fine; the ones that matter pick a *query function* or a redirect from `user` (`EntryDetail` fired the anonymous de-identified RPC this way). Consume via the `useAuth()` hook (`src/hooks/useAuth.ts`), which throws if used outside the provider. `AuthProvider` wraps the whole app in `main.tsx`, above the router.

**Data fetching**: TanStack React Query (`QueryClientProvider` in `main.tsx`) is used for server-state caching in components; the `src/api/` and `src/services/` layers are the underlying query functions, not hooks themselves.

**Routing**: plain `react-router` `<Routes>` in `src/App.tsx` — no nested layouts or loaders. Route groups: auth (`/signin`, `/signup`), entries (`/entry/create`, `/entry/:id`), anime (`/anime`, `/anime/create`, `/anime/:id`), profiles (`/profile/:username`, `/profile/:username/friends`, `/profile/edit`).

**Database schema** (Supabase Postgres): `anime` (external keys: `anilist_id` unique, legacy `mal_id`/`external_id`; franchise grouping via `franchise_key` = AniList id of the sequel/prequel-chain root + denormalized `franchise_title`), `entries` (polymorphic — `entry_type` is `review` | `rating` | `status_update`, with `rating_value`/`status_value` populated depending on type; `rating`-type posts are legacy — rating changes no longer auto-create posts, and the `/entry/:id` page shows the author's **live** current status/rating from `user_anime_entries`/`user_franchise_entries` rather than the frozen post values), `votes` (Reddit-style up/down on entries), `comments` (self-referential `parent_comment_id` for nested replies), `user_anime_entries` (personal watchlist with `status`/`rating`/`review`, per season/movie), `user_franchise_entries` (series-level `status`/`rating`/`review` keyed on `franchise_key` — independent of per-entry statuses and **never auto-reconciled**: a series row is *seeded* the first time a season of a multi-member franchise is added, and after that the user owns it, so nothing ever rolls season changes up into it or removes it. **Neither the seed nor the display fallback ever asserts `completed`** — having watched every season in your list doesn't mean the show is over, and people deliberately keep caught-up ongoing series at `watching`. Declaring a series complete is a claim only its owner makes, so `seriesStatusFor` (`userLists.ts`) and `deriveSeriesStatus` (`utils/listEntries.ts`) both cap at `watching`; keep the two in step. The only other linkage is the optional dismissible "mark all seasons completed?" prompt), `profiles` (with Supabase Storage-backed avatars — see `uploadAvatar` in `src/services/supabase/profiles.ts` for the storage path/URL pattern), `friendships` (`requester_id`/`addressee_id` with `pending`/`accepted`/`rejected` status). Plus one **view**, `franchises` — one row per sequel/prequel chain derived from `anime.franchise_key`, exposing `anilist_root_id` (the `/series/:key` value), `title` (the chain root's own name, often an OVA), `display_title` (the earliest TV member's name — what the UI should headline, computed in SQL the same way `franchiseDisplayTitle` does client-side), `member_count`, `first_year`/`last_year`, and the flagship member's `cover_image_url`/`banner_image_url`. It is a view, not a table, because nothing about a franchise needs *storing* that isn't derivable from its members — promote it the day something does (a curated banner, a manual title override, a slug), and the column names are chosen so that change stays inside `franchises.ts`. Use it whenever you need to name or depict a franchise without needing its members; `fetchFranchiseMembers` is still the right call when you actually render the seasons.

**Visibility (read this before adding any read path)**: Issho is strictly relationship-based — you see your own activity and your friends', nothing else. This is enforced in Postgres RLS, not in the UI. `public.can_view_user(target uuid)` (`SECURITY DEFINER`, checks for an `accepted` friendship in either direction, or `target = auth.uid()`) is the predicate behind the `SELECT` policies on `entries`, `user_anime_entries`, and `user_franchise_entries`; `public.can_view_entry(entry_id)` gates `comments` and `votes` off their parent entry, so a visible thread renders in full. Consequences to keep in mind:
- `get_entries_with_counts` is deliberately **not** `SECURITY DEFINER` — it inherits the `entries` policy, which is why one policy covers the feed, `/entry/:id`, anime pages, series pages, and the Friends page at once. Making it definer would silently reopen global visibility.
- Client-side filters (the `EntryList` tabs, `FriendsPage`'s grouping) split an already-scoped set into views. They are **not** the privacy boundary; never rely on them for it.
- Logged-out visitors have no `SELECT` grant at all. They get `get_public_feed`/`get_public_entry`, `SECURITY DEFINER` RPCs whose return types omit `user_id` and which never join `profiles` — anonymity is a property of the data, not a display flag, so components derive it via `!("user_id" in entry)` rather than an `anonymized` prop. Anonymous viewers get no comments at all, since comments carry identity.
- Deliberately **not** friend-gated for *reads*: `profiles` stays genuinely world-readable (including to `anon`), because username search and add-by-username depend on it. `friendships` reads are open to any *signed-in* user (not just friends of the row's two parties) so friend counts and read-only friends pages work for any authenticated visitor — but `anon` is refused (`to authenticated` on the `SELECT` policy), otherwise a logged-out visitor could crawl the whole social graph via `/profile/:username/friends` without ever signing in.
- `friendships` **writes**, on the other hand, are the authorization boundary — an attacker who can write `status = 'accepted'` grants themselves the whole feed. So: inserts are forced to `pending` (policy `WITH CHECK`), only the addressee of a still-pending row may flip it to `accepted`, `authenticated` holds column-level `UPDATE` on `status` **only** (a table-wide grant would silently re-open the repoint attack, since column revokes can't subtract from it), and a `BEFORE UPDATE` trigger pins `requester_id`/`addressee_id`. Rejecting, cancelling, and unfriending all DELETE the row, so `rejected` is never written — don't add a transition without re-checking the `UPDATE` policy.
- New tables holding user content need their own `can_view_user`-based `SELECT` policy; nothing grants it by default.
- The `franchises` **view** is a deliberate exception: it holds no user content, only public anime metadata, and logged-out visitors reach it alongside the de-identified feed. It is `security_invoker = true`, so it inherits `anime`'s RLS rather than running as its owner, and is granted `SELECT` only. Don't "harden" it with a `can_view_user` policy — that would break the logged-out experience. Note that Supabase's default privileges grant `anon`/`authenticated` **all** privileges on newly created objects in `public`, so a bare `grant select` does not restrict anything; new read-only objects need an explicit `revoke all` first (see `20260728034619_restrict_franchises_view_to_reads`).

**Franchise display**: `src/utils/franchise.ts` groups anime client-side by `franchise_key ?? anilist_id ?? id`; single-member groups render as plain per-anime cards (the two-level series UI only appears for multi-member franchises). Components: `FranchiseCard` (browse grid), `ListStatusButton` (detail page controls, both levels), `ProfileListItem` (profile list, both levels).

**Shared list/edit UI**: the two list levels are unified in the *code*, not in Postgres. `src/types/listEntry.ts` defines `ListEntry`, a tagged union (`kind: "anime" | "franchise"`) over the two physically-separate tables, plus `ListTarget` for addressing a slot that has no row yet. `src/services/supabase/userLists.ts` is the facade every UI surface goes through: it reads both tables into one shape (`fetchUserListEntries`, cached under `userListQueryKey(userId)`) and routes writes back to whichever table an entry came from. `userAnimeList.ts`/`userFranchiseList.ts` remain the per-table query layer and never import the facade.

Because of that union there is **one** of each component where there used to be two: `EditListEntryModal`, `ListStatusButton`, `ProfileListItem` — each branching on `kind` and taking its wording from `src/constants/listEntry.ts`. Extend the shared piece, not a per-level copy. `ModalShell`/`EntryEditModal` own the modal chrome and the numbered status/rating/notes form (with an optional `PostSaveStep` slot, used only for `kind: "franchise"` to swap in `SeasonsCompletedPrompt` after a first-time completion). That prompt is offered from **all three** places a series can become completed — the profile's edit modal, `ListStatusButton`'s picker on `/series/:key` (via `useListStatusEntry`'s `onApplied` callback), and the Create composer (via `publishEntry`'s `seriesJustCompleted`) — each gated on the status having actually *changed* to `completed`. Add a fourth surface and it needs the same gate, or the sweep silently becomes unreachable from there. `StatusOptionList` and `RatingPicker` are shared by that modal *and* the Create composer, so the two can't drift. `useListStatusEntry` owns the add/update-status state machine; `ProfileListCard` owns the presentational card shell.

**Profile list card model**: `UserProfilePage` renders one card per franchise or standalone show, never per season. `src/utils/listEntries.ts`'s `buildProfileListCards` derives these `ProfileListCardModel`s from the same `fetchUserListEntries` union above, grouping per-season entries by franchise and merging in any `user_franchise_entries` row for that key. A series tracked at the series level via "Track whole series" with none of its seasons in the list carries no member metadata of its own, so `franchiseKeysNeedingMembers` finds those orphan keys and the page fetches just those from the `franchises` view (`fetchFranchises`, batched) rather than every member row. `ProfileListItem` renders each card and owns the edit flow, including materializing a series row on first edit of a derived-status series; `ProfileListCard` stays the presentational shell. `ListToolbar` (search + `constants/listSort.ts`) and pagination run client-side over this single card set, matching the fetch-once-then-slice pattern used elsewhere (see **Activity feed** below).

**Who writes to `entries` (the feed)**: only the Create composer (`publishEntry`) and `userLists.ts` writes passed `{ announce: true }` — which is just the detail-page/search `ListStatusButton` add and status change, where the act itself is the statement. Profile edits deliberately write **list state only**: no post is inserted and no existing post is rewritten, because `/entry/:id` already renders the author's live status/rating. Adding a season also seeds a `user_franchise_entries` row for its franchise (multi-member franchises only, **on first add only**, never auto-updated afterwards), so the franchise lands on the profile rather than a lone season — `seedFranchiseEntry` in `userLists.ts` owns that rule and writes nothing to the feed.

**Activity feed** (`src/pages/Home.tsx` + `src/components/EntryList.tsx`): `Home` owns the All/Friends/You filter (`ActivityFilterTabs`, values in `src/constants/activityFilters.ts`) and renders it in the page header; `EntryList` takes the selected filter as a prop, owns pagination, and — on the first page only — renders `FeaturedEntry` (the top hero card) alongside a sidebar stack of `FollowingPanel` (friend avatars + a real "N new entries this week" stat, computed from friends' entries in the last 7 days) and `CreateEntryCta`. Every entry is fetched once (`entriesQueryKey(user.id)`) and filtering/pagination happen client-side, so switching tabs or pages never refetches. The `"all"` filter means *friends + you*, not a global feed — that fetch physically cannot return anyone else. `EntryList` is signed-in only; logged-out visitors get `PublicFeed` instead.

**Friends page** (`src/pages/FriendsPage.tsx`, route `/profile/:username/friends`): a "channels" view (`FriendChannel` — each friend's latest activity, sorted most-recent-first, friends with none last) or a compact alphabetical "directory" list (`FriendDirectoryCard`), both built from the same shared viewer-scoped entries fetch rather than a separate query. Add-by-username (`FriendRequestForm`, which pre-checks friendship status before sending) and incoming requests (`IncomingFriendRequests`) only render on your own page; visiting someone else's friends page shows the same views read-only (no add/incoming-requests/unfriend controls) — but their channels render empty unless you're also friends with that person, since the entries fetch only ever returns your own friends' activity.

**Enums** live as TypeScript string-literal unions in `database.types.ts` (`EntryType`, `AnimeStatus`, `FriendshipStatus`) and are mirrored as Postgres enums. Corresponding UI labels/colors live in `src/constants/` (`animeStatus.ts`, `entryTypes.ts`) — extend these alongside the type union when adding a new enum value.

**Styling**: Tailwind CSS v4 via the Vite plugin (no `tailwind.config` file — config is CSS-based in `src/index.css`). Dark theme (`bg-black text-gray-100`) set at the app root in `App.tsx`.

## Testing

Three layers, each independently runnable — `docs/TESTING.md` is the reference.

- Unit (`src/**/*.test.ts`, Vitest+jsdom) — the `test` block in `vite.config.ts` scopes `include` to `src/` deliberately; the default glob also picks up `tests/rls/` and then fails unless a database happens to be running.
- RLS (`tests/rls/`) — plain `postgres:17`, no Supabase stack. Applies `supabase/tests/harness.sql` then `supabase/migrations/`. The harness deliberately does **not** emulate Supabase's default privileges, so a migration missing a `grant` fails here instead of only in production.
- E2E (`tests/e2e/`, Playwright) — full local stack. Specs mutate shared fixtures on purpose, so `supabase/seed.sql` is self-wiping and re-applied by a Playwright **setup project** (`tests/e2e/seed.setup.ts`), not by the npm script — wiring it into the script instead makes the suite pass in the terminal and fail in `--ui`.
- Local stack quirks: ports are shifted into 544xx (`supabase/config.toml`) and `[realtime]` is disabled because its image exits 1 on arm64 and takes the whole stack down. `supabase status` prints the keys; inspect the database with `docker exec supabase_db_Issho psql -U postgres -d postgres`.
- Mutation-test anything security-critical: break the policy or predicate on purpose and confirm the suite goes red. An assertion like `rows.length <= 200` against a two-row fixture passes whether or not the clamp exists.

## Conventions

- Prettier enforced via ESLint (`prettier/prettier: error`): double quotes, semicolons, 2-space indent, trailing commas (ES5).
- Prefer named Tailwind scale classes over arbitrary bracket values whenever a scale step lands within ~1px (`text-sm` not `text-[14px]`, `h-14` not `h-[56px]`, `max-w-4xl` not `max-w-[900px]`). Reserve `[...]` for values with no reasonable scale equivalent (a specific shadow, a deliberate exact pixel width, grid-template-column tracks like `grid-cols-[1fr_auto_1fr]`).
- Most files carry a header comment with their path and one-line purpose (e.g. `/** src/services/anilistApi.ts ... */`) — follow this pattern for new files in `services/`, `api/`, `context/`, `hooks/`.
- Supabase MCP is configured (`.mcp.json`) against the live project — schema changes via MCP tools go straight to the remote project. Mirror every applied migration into `supabase/migrations/<version>_<name>.sql` so the schema stays reviewable in git, and name it so it sorts *after* `20260101000000_baseline_schema.sql` (the reconstructed `create table` baseline everything else patches). `supabase/migrations/archive/` holds the pre-baseline patches — read them for commentary, never re-run them.
- There is no database password on hand, and `supabase db pull` / `supabase link` require one. Reconstruct or verify remote schema through Supabase MCP catalog queries (`execute_sql` against `pg_policies`, `pg_get_functiondef`, `pg_constraint`) instead.
- Before starting work in a session, confirm `git branch --show-current` matches the feature branch the task is actually for (feature branches here are named `<issue-number>-<slug>`, e.g. `21-feat-updateimprove-profile-settings-page`) — don't assume the checked-out branch is correct just because it's what's active. If it doesn't match, stop and flag it rather than committing work to the wrong branch.
- Never run `git commit` (including from `/simplify`, `/code-review` apply steps, or any other automated flow) without the user explicitly telling you to commit in that turn. Leave finished work as uncommitted changes for review by default.
- When asked to commit a session's work, group commits logically by the distinct pieces of work done rather than one commit for everything touched — split by feature/fix/area, not by chronological order, so each commit stays traceable and reviewable on its own. Files that mix an intentional change with a bundled review-fix to that same file can stay together in one commit rather than being split at the hunk level; the goal is a commit history a reviewer can follow, not a mechanically clean diff.
